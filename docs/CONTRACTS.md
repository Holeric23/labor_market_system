# Контракты системы

## Эксплуатация и восстановление — этап 11

Этап выполняется после завершённого этапа 10, без публикации или изменения внешних сервисов. `market_system.operations` — общий CLI: init, create-admin/create-user, web, worker, bot, launch, diagnose [--full], backup, verify-backup, restore. По умолчанию local/127.0.0.1, polling=false/delivery=false. Секреты и рабочие аккаунты вводит пользователь отдельно; отсутствие настоящих токенов не подменяется фиктивным подключением. Linux unit/proxy-шаблоны не объявляются проверенными без исполнения на Linux.

`config/operations.json` имеет строгую схему: mode, runtime, web_state, bot_state, bot_env, host, port, allowed_hosts, bot_enabled, delivery_enabled, log_bytes/log_backups, shutdown_seconds, source_freshness_hours. Runtime сохраняет прежние шесть ключей. `MARKET_HOME` выбирается до Python-импорта; пути остаются внутри этого корня. Старый Python_research_project, выход за корень, symlink наружу и hard-linked рабочие файлы отклоняются. Защита Python audit проверяет реальные пути записи без подмены aliases; это не OS-песочница для чужого native-кода. Временные каталоги, matplotlib/pip/XDG/Playwright кеши направляются в `.artifacts`.

Веб, исполнитель и необязательный бот используют одну конфигурацию и постоянные локальные SQLite. Worker остаётся единственным, под прежней OS-блокировкой. Launcher имеет отдельную блокировку, запускает только выбранные компоненты, закрывает весь комплект при выходе одного компонента. Для остановки используется cooperative stop между пакетами с ограниченным ожиданием, затем полное дерево: Windows Job Object с assignment-barrier до появления потомков; Linux process groups, а в systemd KillMode=control-group. Running processing/collection сохраняют checkpoint и восстанавливаются прежними recover, не объявляются отменёнными/успешными. Слишком долгий сетевой/ML-вызов может потребовать принудительной остановки после shutdown_seconds; атомарность прежних SQL-транзакций сохраняется.

JSON-логи UTC/level/component/pid/logger/message ограничены ротацией по размеру, отдельный файл на компонент. Значения секретных environment-переменных, Bot API token и URL очищаются, raw traceback не сохраняется; HTTP query access logs выключены. По умолчанию 5 MiB + 4 резервных файла на компонент. SQLite-аудит/история/backup не удаляются автоматически: владелец контролирует диск и сохранность копий. Linux создание постоянных файлов использует umask 0077, state/secrets/backups закрыты от других пользователей. Windows ACL на собственные секреты настраивает пользователь.

Read-only diagnose проверяет существование/quick_check/FK SQLite, точные миграции 1–8 с SHA-256, active ready и соответствие реестру, очереди processing/collection, pending handoff, delivery debt, needs_update-подписки и незавершённые experiments. Возраст источника считается по last_success_at; неизвестное время остаётся unknown, отсутствие managed_sources не означает свежесть. Full дополнительно проверяет integrity_check/точное покрытие ready и файлы/зависимости текущей модели до десериализации. Ошибки дают exit 1, предупреждения перечисляются отдельно. ADMIN-only `/diagnostics` выполняет быструю проверку, без ML, новых заданий или детализации личных получателей/фильтров. Все прежние ADMIN/USER/CSRF-границы сохраняются; ADMIN не получает права менять чужие Telegram-подписки. CLI подразумевает OS-доступ владельца, USER не должен иметь доступа к файлам SQLite/копиям.

Backup v1 — отдельный новый каталог в backups/ или .artifacts/. Сначала захватывается блокировка исполнителя (работающий worker приводит к отказу). Затем отдельные BEGIN IMMEDIATE удерживают запись во все существующие app/web/bot/annotations SQLite одновременно. Backup API отдельными читающими соединениями снимает их committed-состояние, включая WAL; снимки переводятся в DELETE journal mode. Модели/реестр кандидатов/файлы processing-spec, словари, архив разметки, CSV источников и код копируются обычными файлами с SHA-256 до/после. В архив входят source, SQL/templates/static, инструкция, locks и vendor; окружения, кеши, секреты и Telegram-сессии исключены. Manifest с отдельным SHA-256 фиксирует inventory/размеры/checksums/runtime/migrations/origins. Manifest записывается последним; частичный каталог без него непригоден. Verify открывает SQLite с immutable=1 и не создаёт WAL в архиве. SHA-256 проверяет целостность, не авторство архива.

Restore запрещает существующий target, рабочий корень, вложение target в bundle и выход конфигурационных путей за destination. Inventory/SHA-256/SQLite/FK/миграции проверяются до копирования; затем сверяются скопированные bytes. Неизменяемые spec_json, их исторический fingerprint и научные данные не переписываются. Ограниченные прежние корни записываются в config/relocation.json; runtime-resolved копия processing-spec проверяет исходный fingerprint, разрешает только локальные файлы и вычисляет fingerprint локальных путей в памяти. Путь, уже находящийся внутри текущего MARKET_HOME, никогда не подменяется повторно, включая восстановление внутри прежнего корня.

В восстановлении mode=local, bot_enabled/delivery_enabled=false; web_sessions удаляются, аккаунты/хеши паролей/подписки/jobs сохраняются. Не копируются и не создаются настоящие Telegram credentials. Отдельный процесс с restored src выполняет full diagnose в destination, сохраняет restore-verification.json и при несовместимости оставляет каталог для разбора, не меняя рабочую систему. Поиск/карточка читают сохранённый ready-набор; worker использует runtime-resolved неизменяемую модель. Прежние низкоуровневые исследовательские CLI остаются историческими инструментами; после переноса следует использовать общий operations для эксплуатационного запуска и проверки, явно задавая восстановленный корень. Массовый processing, обучение, автоактивация и внешняя отправка не входят в проверку копии.

Windows/Linux locks фиксируют версии и SHA-256 выбранных CPython 3.12 x86_64 wheels, включая локальный pure-Python pyaes в vendor. Linux cross-platform-проверка доступности wheels не подтверждает зависимость ОС, перезагрузку, TLS или Linux-исполнение. Будущие units используют постоянный `/srv/labor-market`, отдельного системного пользователя, один worker, Restart=on-failure и WantedBy=multi-user.target; бот отдельно optional. Reverse proxy слушает HTTPS, Python — только loopback, Secure cookie включён в linux mode, forwarded scheme доверяется только 127.0.0.1. Реальные domain/DNS/certificate/firewall/secrets и Linux-верификацию выполняет пользователь отдельно.

## Управление моделями и исследованиями — этап 10

Этап выполнен после аналитики этапа 9. Миграция 8 добавляет `model_registry`, `model_class_definitions`, `model_events`, `model_experiments`. Прежние миграции и физические таблицы классов/связей не пересоздаются. `Models.initialize` выполняет только миграции: не загружает ML, не обучает, не запускает worker, сбор или эксперимент. Регистрация доверенного локального комплекта — отдельная ADMIN-команда.

Реестр хранит candidate/approved/active/retired, исходный manifest, пути локальных артефактов и SHA-256, зависимости, историческую область оценки, фиксированную спецификацию исполнения и полное пространство определений. Регистрация идемпотентна только для идентичной спецификации. Изменение артефактов, словарей, смысла или кода требует новой версии; существующий manifest не переписывается. При первичной регистрации уже используемого Ensemble состояние active устанавливается по существующему указателю без смены выдачи. active далее следует за рабочим ready-набором в той же SQL-транзакции; прежняя модель остаётся approved для отката. Вывести рабочую модель в retired нельзя до переключения; возврат retired требует явного approved.

Единый интерфейс `model_management.adapters.load(spec).predict(texts)` возвращает прежние строки LaborMarketPipeline. Allow-list содержит только `ensemble-v1`: проверяются обязательный формат manifest, веса, пороги, политика, preprocessing, пути, SHA-256 и точные runtime-версии numpy/pandas/sklearn/CatBoost/joblib. Зависимости исследовательского построения графиков и исторический Python записаны в manifest, но не объявляются обязательной версией интерпретатора исполнения; Ensemble фактически проверен в локальном Python 3.12. Ошибки десериализации оборачиваются в понятный `IncompatibleArtifact`. Проверка checksum выполняется до десериализации. Форматы multiclass/two_ovr/two_pairs/three_pairs, массивы `.npz` и произвольный research joblib не имеют подтверждённого deployment-формата и отклоняются. Наличие CSV метрик не подтверждает совместимость модели.

`Models.designate(version, ADMIN)` в одной BEGIN IMMEDIATE одобряет candidate и создаёт полное processing job со снимком всех текущих content ID/SHA-256 и публикаций, спецификацией классов/словарей/кода и записью аудита. При ошибке создания задания одобрение и задание откатываются. Выполняет задание только явно запущенный существующий единственный worker; назначение не активирует результат. Корпус, классы и входные публикации закреплены до исполнения. Неизвестный машинный класс вне class_space отклоняется; документ без классов имеет явный no_classes. Сбой остаётся failed в jobs с ошибкой; частичный result_set остаётся building для прежнего retry/checkpoint, не становится видимым. Обычные processing jobs и handoff сборщика после переключения берут спецификацию из активного реестра, не возвращаются к старому runtime model.

ADMIN активирует только проверенный ready-набор через прежний `activate`: текущие confirmed-исправления, согласование подписок этапа 8, указатель каталога, состояния реестра и история переключения фиксируются атомарно. Прежний набор сохраняется. Откат — та же операция для прежнего ready ID; при более свежих исправлениях создаётся ready-производная версия с этими исправлениями, исходная остаётся неизменной. Для нового смысла, разделения/слияния классов создаются новые определения/namespace по полному содержимому словаря, даже при совпадении имени или заявленной версии словаря. Названия не являются соответствиями. Перенос подписок требует явных подтверждённых ID-соответствий; при обратном переключении также требуется обратное соответствие. Человеческие классы сохраняются по правилам этапа 8. Пересборка старого корпуса не создаёт массовой рассылки.

`model_management experiment VERSION --ids ... --max-documents N --seconds S --cohort ...` — явная оценка фиксированной модели, без обучения и автоматического выбора параметров. Обязательный бюджет: 1..100 уникальных документов, 1..300 секунд дочернего процесса, включая загрузку/предсказание. Бюджет не ограничивает время предварительного снимка/миграций и не является ограничением памяти. Родитель удерживает ту же OS-блокировку исполнителя, запускает отдельный процесс и при timeout завершает его, сохраняя failed. При аварии самого родителя запись может остаться running: она не перезапускается и не выдается за завершённую. История фиксирует бюджет, spec SHA-256, точные входы и SHA-256 текстов, происхождение человеческих меток/исправлений, все исходные memberships и когорты, публикации/источники, scope, ошибки, precision/recall по типам, coverage, refusals, время, precision/recall/покрытие отдельных полей и подтверждённое отсутствие. Исходный текст остаётся в contents один раз. Ошибки типа перечисляются по content ID. Неизвестная/несовместимая разметка поля исключается с числом; отсутствие подтверждённой разметки даёт NULL метрики, не оценку качества. Человеческие классы сравниваются по namespace/key и роли, не по названию.

`selection` разрешает только development без пересечения с train/test/challenge по content ID и сохранённой группе. Test/challenge допускаются только как diagnostic, параметры и пороги не подбираются. Каждая историческая оценка имеет independent_audit=false; test обозначается retrospective, дополнительно сохраняется historical_test_overlap даже для development-выборки. Ноль ошибок validation не гарантирует качество. Повторно исследованный исторический test не является новым независимым аудитом.

Явный `import-history DIRECTORY` читает только данные JSON/CSV известных отчётов из указанного read-only архива: протоколы/параметры, выбор моделей, метрики, warnings/failures, test_errors. Ни исходный код, ни модели, ни benchmark не исполняются. Снимки отчётов и хеши сохраняются в новой БД; рабочее приложение больше не обращается к старому проекту. Один файл до 2 MB сохраняется целиком; более крупный сохраняет SHA-256/размер с data=NULL. Исторические таблицы не переименовываются в независимый аудит, исходный scope (в том числе agent silver) сохраняется. Повторный импорт идентичного архива идемпотентен.

В существующем приложении ADMIN-only `/models`, `/models/{version}`, `/experiments/{id}` и JSON-выгрузка показывают статусы, артефакты/хеши, определения, параметры, происхождение, метрики и ошибки. POST approve/retire/designate/activate требуют ADMIN и CSRF. HTTP не принимает путь к joblib, не выполняет ML и не начинает эксперименты. Просмотр длинной записи ограничен 50 000 символами, полный сохранённый JSON доступен в выгрузке. Новые научные срезы дополнительно фиксируют семантические определения и неизменяемые поля реестра; старые срезы читаются по своим сохранённым inputs/reports/code без пересчёта.

## Аналитика ADMIN и научные срезы — этап 9

По прямому запросу пользователя аналитика выполнена на этапе 9 после этапа 8. Исторический объём исправлений уже выполнен на этапе 7; исходная нумерация system_plan.md не означает выполнение следующего этапа.

`Analytics(db)` читает общий ready-каталог. ADMIN-only `/analytics` предоставляет шесть отчётов: документы/публикации по UTC-дням и источникам; частота профессий/навыков; навыки по профессиям; независимые условия работы/занятости; распределения указанных границ зарплаты; качество полей. Общий фильтр действует на каждый отчёт: start включительно, until исключительно (полночь UTC), точные source ID и необязательный тип документа. При ограничении периода/источников выбираются подходящие result_publications, затем уникальные документы; документы без подходящей публикации исключаются. Без ограничений учитываются также документы без публикаций и неизвестные даты. Отчёты разделяют vacancy/resume/неуказанный тип. Версия ready-набора закреплена в ссылках просмотра, выгрузки и сохранения.

Документ — сохранённый уникальный исходный текст (content_id), публикация — ID публикации. Повторная публикация текста не увеличивает число документов или доказанное число вакансий. В группах день/источник документ может присутствовать повторно; сумма групп не равна размеру уникального корпуса. Близкие, но разные тексты автоматически не объединяются. Навык с точным class ID учитывается один раз на документ независимо от числа упоминаний и сочетания required/preferred; для resume допускается только possessed. Названия классов не объединяются. Навыки по профессиям допускают только единственную профессию; множественные профессии исключаются из этого отчёта с числом и списком документов.

Применённая confirmed-аннотация имеет приоритет над машинными статусами неоднозначности. multiple_offers исключает документ из частот, связей навыков с профессиями, условий и зарплат; объём и качество сохраняют его. Неоднозначные отдельные условия исключаются из соответствующего поля, остальные поля могут участвовать. salary_scope=unattributed исключает зарплату; NULL не превращается в 0. Отдельно показываются исключённые документы и суммы с неизвестной валютой/периодом. Неизвестный период не считается month. Валюты, периоды, gross/net/неизвестный tax_mode, тип документа и нижняя/верхняя границы распределены по раздельным группам. Нет обменных курсов, среднемесячного пересчёта, средних вилок или комбинаций «каждая зарплата × каждая профессия».

Отчёт качества содержит missing/ambiguous/known по каждому полю, включая обе границы зарплаты. Эти состояния взаимно исключаются; verified — отдельная пересекающаяся доля применённых confirmed-ревизий, в том числе подтверждённого отсутствия значения. Draft/uncertain и историческая разметка только типа не дают verified. Знаменатель — вся выбранная выборка уникальных документов; у пустой выборки доля NULL. Нулевое количество пустой категории не означает заполнение неизвестной суммы нулём. Дата публикации не объявляется проверенной подтверждением аннотации извлечённых полей.

Каждый отчёт содержит единицу подсчёта, размер выборки, версию, фильтры, числа исключений и переход к документам каждой группы/исключения. CSV выгружается в ZIP вместе с manifest.json: условия, метаданные ready-набора, модель/экстракторы/словари, определения классов, версия и SHA-256 алгоритма/входов/отчётов, единицы и исключения, SHA-256 каждого файла. CSV хранит NULL в измерениях как JSON null, а не как нулевую сумму; document_ids_json позволяет независимо проверить основания. Интерфейс показывает до 50 групп/документов на странице; CSV содержит полный отчёт. Ограниченность выбранных источников явно указана; выводы обо всём рынке не делаются.

Миграция 7 добавляет append-only scientific_slices и scientific_documents. `save` в одной BEGIN IMMEDIATE фиксирует конкретный ready-набор, эффективные поля/связи, точные применённые ревизии (включая автора, время, аннотацию, происхождение), исходные публикации/названия источников, определения классов и подтверждённых новых терминов, фильтры, версии, контрольные суммы, исходный код автономного алгоритма и готовые результаты. Исходный текст остаётся один раз в contents; scientific_documents фиксирует точный SHA-256 и FK, триггеры запрещают изменение/удаление текстов, вошедших в срез. Аналитические входы сохраняют необходимые машинные статусы и контрольные суммы полного profile/skills evidence; исходное полное evidence остаётся в неизменяемом ready-наборе. Сохранение не изменяет active и не запускает ML, сбор, рассылку или обучение.

`load` проверяет контрольные суммы фиксированных входов/результатов/кода и возвращает сохранённый результат, не вызывает текущий алгоритм, активный каталог или новые исправления. Карточка среза читает сохранённые поля, публикации, определения и исправление, проверяет точный SHA-256 исходного текста; она не зависит от актуального имени источника. Новые исправления, активация другого набора и обновление расчётного алгоритма не меняют прежний срез. ID активного каталога сам по себе научным срезом не является.

Полный ZIP включает inputs.json с точными исходными текстами, reports.json, CSV, engine.py и manifest.json с SHA-256 файлов. Архив является самостоятельной научной копией: `python engine.py inputs.json replay.json` выполняется только на стандартной библиотеке, без рабочей БД и пакета market_system; SHA-256 replay.json должен совпасть с files_sha256[reports.json]. SHA-256 inputs в checksums относится к каноническим входам БД с ссылками на тексты; files_sha256[inputs.json] — к переносимому файлу с самими текстами. Исходные тексты в архиве сверяются с индивидуальными SHA-256. Код архива не исполняется сервером из БД.

Все HTTP-чтения, переходы и выгрузки закрыты для USER; POST сохранения требует ADMIN и CSRF. При выборе малого периода SQL ограничивает загрузку связей, исправлений и evidence выбранными документами. Расчёт и сериализация полной выборки требуют памяти/времени пропорционально корпусу; сохранение удерживает транзакцию записи. Нагрузочное измерение полного корпуса и визуальная проверка браузером отдельно не проводились. Изменение версии алгоритма требует нового versioned-модуля для новых расчётов; старые сохранённые результаты и автономный исходный код сохраняются.

## Telegram, подписки и outbox — этап 8

Миграция 6 хранит доступ, структурированные подписки, соответствия классов, границу известных текстов, outbox, попытки и квитанции в `data/app.db`. Это общая транзакционная граница с ready-данными. При установке весь существующий корпус записывается в telegram_seen по SHA-256 точного текста: старые данные не образуют очередь рассылки. Миграция не создаёт пользователей, подписок или отправок.

Рабочий sqlite-backend aiogram использует `CatalogSearch` → общий `Catalog.search` и `SearchFilter.normalized`; SQL-семантика совпадает с вебом, включая роли навыков, ALL/ANY, неизвестные значения, строгую валюту/период зарплаты и границы дат. Telegram принимает JSON-фильтр; даты ISO содержат часовой пояс (веб переводит свои даты в полночь UTC). Поиск и /next сохраняют отдельную сессию в БД. Подписка никогда не содержит курсор/offset/limit; попытка передать их отклоняется. Непригодный после смены набора курсор требует нового поиска.

Доступ закрыт по умолчанию. Локальная настройка ADMIN_USER_IDS создаёт ADMIN в telegram_access; прежнее имя параметра сохранено для совместимости. ADMIN допускает USER командой /allow TelegramID, отзывает /deny. Конфигурация не удаляет уже зарегистрированных владельцев автоматически. Middleware пропускает только разрешённого пользователя в его личном чате. Сервис повторяет проверку доступа; просмотр/создание/удаление подписок всегда ограничены собственным user_id, включая ADMIN. Telegram и веб используют отдельные учётные записи.

Сохранены транспорт AiogramTelegramClient, AuthMiddleware, UIMessageManager, разбиение текста по UTF-16 и прежний StateDatabase для постоянных UI-данных. Старые подписки из state/bot.db импортируются с владельцами и исходным фильтром, получают needs_update: названия не преобразуются в ID. Старые файлы, события и квитанции не удаляются. Новый автоматически импортированный USER отключён до разрешения ADMIN. Прежние доменные сервисы и memory-backend оставлены для автономных проверок/демонстрации; рабочий режим — sqlite.

Producer реально вызывается при финализации processing job и построении каталога из сохранённых результатов. В одной транзакции фиксируются ready, telegram_seen, outbox, получатели и завершение задания. Ошибка записи события откатывает готовность и события. Полные и incremental-наборы уведомляют только о ранее не наблюдавшемся уникальном тексте вакансии с исходной публикацией. Sample не публикует события. Повтор текста, новый источник того же текста, новая модель старого корпуса, изменения типа/полей старой карточки и человеческое исправление не создают повторной рассылки. Новая ревизия текста старого URL также не считается новой вакансией. Первый ready нерелевантного или не подошедшего подпискам текста всё равно фиксирует наблюдение: более поздняя подписка не рассылает историю.

Сопоставление подписок компилирует тот же `compile_page`, без отдельного Python-matcher. Событие содержит стабильный UUID5 от SHA-256 текста, ссылку на неизменяемый ready-набор/документ и версию отображения; исходный текст повторно не хранится. Уведомление строится из этого снимка, содержит ID события и помещается в одно сообщение. Два совпавших фильтра одного пользователя дают одну доставку. Получатели фиксируются при ready. Это готовность конкретного снимка, а не активация: уведомление может ссылаться на новую публикацию до ручного переключения рабочего каталога. Автоматической активации по-прежнему нет.

При смене модели машинные классы подписки переносятся только через /map OLD_ID NEW_ID MODEL_VERSION, подтверждённый ADMIN. Совпадение названий не используется; консервативно требуется явное соответствие и для прежнего ID при смене модели. Подтверждённые human-ID сохраняют свою независимую идентичность. Без соответствия подписка получает needs_update с объяснением в /subscriptions и не сопоставляется новым данным. Владелец может подтвердить соответствие, пользователь — удалить старую подписку и создать новую. Уже сформированное событие сохраняет прежний снимок и получателей. Удаление подписки или отзыв доступа отменяет её ещё не начатую доставку; начатая внешняя отправка имеет обычное окно гонки с отзывом.

Доставка исполняется существующим worker под общей OS-блокировкой. Она включается только явным `jobs worker --telegram-env <локальный env>`. Без флага события остаются в БД. Каждая попытка имеет время/номер, running-владельца, исход и при успехе Telegram message_id/sent_at. При перезапуске running становится queued, старая попытка — interrupted. Временные ошибки повторяются с задержкой (30 секунд с ростом до часа, RetryAfter — указанная задержка до суток); постоянный отказ даёт failed. Отозванный доступ/удалённая подписка дают cancelled. Ответ Telegram и запись квитанции не могут быть одной транзакцией: авария после send до commit может дать повтор с тем же ID события. Абсолютная однократность не обещается.

Рабочий HTTP-получатель удалён из запуска: EVENTS_ENABLED=true отклоняется, порт не открывается. Исторический аутентифицированный helper в presentation/events остаётся только для совместимости автономных тестов, production его не подключает. Межпроцессного HTTP-producer нет и он не нужен: producer пишет SQLite напрямую. Секреты не входят в repr настроек, логи очищаются, ошибки доставки сохраняются без исходного исключения. Тесты используют имитацию Telegram; живой запуск требует отдельной локальной настройки токена.

## Единая проверка документов — этап 7

Миграция 5 отделяет `review_revisions` от машинного `result_evidence`. Ревизия содержит content_id, возрастающий номер, draft/confirmed/uncertain, автора, время, полную аннотацию и происхождение. Записи неизменяемы. Новая запись проверяет ожидаемый номер внутри BEGIN IMMEDIATE; веб дополнительно проверяет ожидаемый активный набор. Конфликт возвращает 409. Старый подтверждённый вариант действует, пока новая ревизия остаётся draft или uncertain.

Аннотация включает тип, список профессий, навыки с ролями, зарплатные предложения, условия, признак нескольких предложений и комментарий. Пустой список означает явное отсутствие; редактор позволяет добавлять пропущенные значения. Подтверждение заменяет все эффективные поисковые связи документа, включая удаление отменённых навыков и старого типа, в одной транзакции. Машинные основания показываются отдельно и не переписываются.

При подтверждении для обработанного документа создаётся building-копия активного набора, применяются актуальные подтверждения, проверяется полнота исходного корпуса, обновляются счётчики, затем набор становится ready и переключается указатель. Ревизия, связи, поля, применение ревизии и указатель фиксируются атомарно. Ошибка откатывает всё. Прежние ready-наборы и научные архивы неизменны. Первая реализация копирует весь набор: это затраты времени, места и длительная транзакция записи на большой БД; оптимизация снимков не входит в этап.

`result_review_applications` фиксирует точную ревизию для каждой пары набор/документ. Чтение явно выбранного старого снимка возвращает его прежние значения. Новая обработка, включая смену модели, применяет последнюю confirmed-ревизию перед переводом building в ready. Активация старого ready также строит новую копию при наличии более свежих подтверждений. Входной список ML остаётся зафиксированным; правила актуализации человеческих исправлений не меняют корпус. Для ещё необработанного документа подтверждение сохраняется до обработки. ML внутри HTTP не запускается.

Классы задаются точными ID с namespace/version. Новое слово сначала создаёт `review_terms`, затем ADMIN отдельно подтверждает словарное определение. Только после этого возможна confirmed-ревизия с этим термином. Совпадающие названия не объединяют классы. Новые определения получают собственный namespace; автоматическое переобучение и изменение словаря извлекателя не выполняются.

`/review` предоставляет очереди случайного аудита, неуверенного типа, неоднозначных полей, новых терминов и нескольких предложений. Аудит сохраняет случайную выборку; чтение не меняет её. `/review/{content_id}` — единая форма и история. Все чтения и изменения редактора доступны только ADMIN, записи защищены CSRF. USER видит эффективный каталог без доступа к редактору. Старый неавторизованный research review_server отключён; перенесённый архив аннотаций доступен только для чтения.

Явный `review import-legacy` переносит исходные когорты train/development/test/challenge, группы, внешние ID, контрольные суммы, исходные номера ревизий и аннотации. Неизвестный исторический автор остаётся NULL. Повтор импорта идемпотентен; изменение зарегистрированного источника отклоняется. Отсутствующий документ в файле обучающих меток сохраняется как membership без content_id. Прежние обучающие метки типа хранятся отдельно в `review_type_labels` и не подтверждают извлечённые поля. `review_training_candidates` допускает только явный train с confirmed и исключает любой test/development/challenge; представление само ничего не обучает. Научные файлы и их исходные разбиения не изменяются.

Для нескольких предложений хранится только пометка, без автоматической сегментации. Неоднозначные зарплаты очищаются в эффективном каталоге, получают salary_scope=unattributed. Представление `salary_occupation_facts` допускает только ready-вакансии с единственной профессией, однозначной зарплатой уровня документа, известными валютой/периодом и без multiple_offers. Это обязательная граница будущей аналитики зарплаты по профессии.

## Продукт и архитектура

Локальное модульное Python-приложение для одного владельца, впоследствии для владельца и друзей на сервере. SQLite; веб на FastAPI/Jinja2 для администрирования и поиска; aiogram для Telegram-поиска и подписок; один исполнитель постоянных заданий. Без микросервисов, Redis, Elasticsearch и отдельного SPA.

ADMIN управляет источниками, обработкой, исправлениями, версиями и системой. USER ищет и меняет только собственные подписки. Приоритет вакансий; резюме сохраняются для научной работы. Неизвестное значение не превращается в ноль, отрицание или предположение. Источники ограничены существующими TelegramParser и DesignHuntersParser. На первом шаге только точная дедупликация; автоматическое выделение нескольких вакансий из поста отложено.

## Версии и публикация

Версия модели, запуск обработки и снимок корпуса — разные идентификаторы. Текущий `save_snapshot` с полной версией корпуса сохраняется как исследовательский контракт; ежедневная обработка порций требует отдельного интерфейса на следующем этапе. Новый набор строится рядом с действующим. После проверки полноты, ссылочной целостности и совместимости единый указатель active_result_set переключается транзакционно. Веб и бот читают один набор; прежний сохраняется для отката. Исторические снимки не переписываются человеческими исправлениями.

## Планируемые границы служб (исторический план этапа 0; реализация поиска уточнена в разделе этапа 3)

## Окончательная схема поисковых данных — этап 2

Код миграции: `src/market_system/search/001_search.sql` и транзакционная обвязка `search/store.py:migrate`. Миграция №1 регистрируется в `schema_migrations(version PK, sha256, applied_at)`. Повторный запуск не меняет схему; несовпадение контрольной суммы SQL отклоняется. Чистая SQLite получает существующие базовые таблицы source_types/sources/contents/publications, перенесённая сохраняет их. Новые таблицы не зависят FK от наличия legacy extraction-таблиц: чистая схема пригодна для следующего наполнения; сборка сохранённого набора требует реальные сохранённые прогоны.

| Таблица | Окончательные поля и ограничения |
|---|---|
| result_sets | result_set_id TEXT PK; model_version, skills_run_id, profiles_run_id TEXT NOT NULL; versions_json, provenance_json, coverage_json — валидный JSON; state ∈ building/ready/failed; created_at NOT NULL, ready_at, error |
| classes | class_id INTEGER PK; namespace, class_key, name, definition_version TEXT NOT NULL; UNIQUE(namespace,class_key); namespace/class_key непустые; реестр append-only |
| document_processing | PK(result_set_id,content_id); FK к result_sets и contents; status processed/no_classes; наличие строки означает завершённую обработку документа, отсутствие — не обработан |
| document_classes | PK(result_set_id,class_id,content_id,role); role TEXT NOT NULL DEFAULT 'none', непустая; score NULL либо 0..1; FK к classes и составной FK к document_processing |
| search_catalog | PK(result_set_id,content_id), составной FK к document_processing; post_type vacancy/resume/NULL; published_at_utc; publication_count ≥0; salary_from/to, currency, salary_period, tax_mode; work_format, schedule, employment_type, working_hours, hours_per_week; review_status unreviewed/needs_review; salary_scope document/unattributed |
| result_evidence | PK/FK(result_set_id,content_id); classification_json, profile_json (допускает NULL), skills_json — снимки сохранённых результатов/упоминаний, без копии исходного текста |
| result_publications | PK(result_set_id,publication_id); FK publication_id → publications; FK(result_set_id,content_id) → document_processing; published_at_utc; фиксирует группировку публикаций и дату в данной версии |
| active_result_set | singleton INTEGER PK CHECK(singleton=1), result_set_id FK NOT NULL; до первой активации таблица пуста |
| result_set_switches | id INTEGER PK, previous_id nullable FK, result_set_id FK, switched_at; история явных переключений/откатов |

`contents.text_hash` по-прежнему UNIQUE. Текст хранится только в contents; карточка ссылается на content_id. У одного документа любое число классов и разные роли; повтор ровно той же четвёрки запрещён. `none` — единственное обозначение отсутствия специальной роли, не NULL и не пустая строка. Для навыков сохраняются required/preferred/possessed; повторные упоминания одной пары skill+role дают одну связь. Score при переносе навыков/профессий NULL: словарное совпадение не объявляется вероятностью.

Обязательные индексы:

- `document_classes_forward(result_set_id,class_id,role,content_id)`;
- `document_classes_reverse(result_set_id,content_id,class_id,role)`;
- `catalog_date(result_set_id,post_type,published_at_utc,content_id)`;
- `catalog_salary(result_set_id,currency,salary_period,salary_from,content_id)`;
- `result_publications_content(result_set_id,content_id,publication_id)`.

### Определения и версии

Namespace определяет точное пространство определений: `skill:<сохранённый lexicon_sha256>`, `occupation:<SHA256 канонического сохранённого occupation_lexicon>`, `post_type:<model_version>`. class_key — исходный стабильный код, name — отображаемое имя; definition_version — исходная версия словаря или модели. Одинаковое name у разных class_key/namespace не объединяет классы. Несовместимое повторное определение той же пары namespace/class_key отклоняется. При изменении смысла/словаря создаётся другой namespace, старые строки сохраняются. Добавление класса в неизменённое пространство — INSERT, без DDL. Переименование существующей строки на этом этапе не поддерживается (триггер неизменяемости).

versions_json фиксирует версии skill/occupation/salary/work-condition экстракторов, версию и хеш обоих словарей. provenance_json содержит копии метаданных выбранных трёх прогонов, их происхождение, политику проекции и явное no_inference=true. Служебное model_version='pending' используется только до разрешения совместимой модели или при раннем отказе; готовый набор содержит настоящий model_version.

coverage_json готового набора: expected (снимок числа contents), document_processing, search_catalog, result_evidence, document_classes (число связей), no_classes. Прогресс не выводится из отсутствия связей: обработанные документы без классов имеют явную строку no_classes. Все исходные документы, включая неуверенно классифицированные, получают учёт и карточку с post_type=NULL.

### Построение без извлечения

`build(db, skills_run, profiles_run, identity=None)` требует явно выбранные runs, совпадение model_version, входного input_sha256, полное покрытие классификации и полное совпадение target-документов, типов и версий обоих extraction-прогонов. Дополнительно сверяется объявленное число профилей. Выбираются сохранённые строки, не вызываются модель, обучение или extractors.

Навыки: для vacancy только required/preferred, для resume только possessed. Остальные упоминания остаются в исходных таблицах и result_evidence, но не становятся поисковыми связями. Профессии берутся из сохранённого occupation_ids_json, названия/определения — из словаря в metadata данного профиля. Тип vacancy/resume также представлен классом с role=none. Поиск по спискам должен использовать document_classes, не json_each; JSON распаковывается только при построении проекции и просмотре доказательств.

Даты: только даты с явным часовым поясом нормализуются в фиксированный UTC-формат `YYYY-MM-DDTHH:MM:SS.ffffffZ`. Дата без timezone, невалидная или отсутствующая → NULL, без предположения о локальном часовом поясе. Карточка хранит последнюю известную нормализованную дату среди её публикаций и полное количество публикаций; отсутствие актуальности вакансии не подменяется датой публикации.

Один content — одна карточка. При нескольких occupation_ids или salary_status=needs_review зарплатные фильтруемые поля обнуляются в NULL, salary_scope=unattributed, review_status=needs_review; исходные зарплатные значения и упоминания остаются в result_evidence/legacy. Несколько профессий — консервативный признак неоднозначной привязки, а не утверждение, что пост содержит несколько вакансий. Автоматического разделения постов и связей «каждая зарплата × каждая профессия» нет. Неизвестные единицы оплаты/условия остаются NULL. Подтверждённая человеческая разметка на этом этапе в карточки не проецируется: статуса confirmed нет, исходная разметка сохранена отдельно.

### Транзакции и откат

`migrate` использует BEGIN IMMEDIATE и отдельное выполнение DDL без неявного commit executescript; ошибка откатывает все изменения миграции. `market_system.sqlite.connect` включает и проверяет PRAGMA foreign_keys=ON на каждом соединении приложения, включая read-only.

Сначала создаётся building-запись; затем одной отдельной транзакцией строятся новые строки. Готовность проверяется по количеству документов/карточек/evidence, статусам no_classes, FK и группировке публикаций. После проверки набор переводится в ready. Исключение откатывает построенные данные, фиксирует failed и error; активный набор не затрагивается. При аварийном завершении процесса building может остаться для явного разбора, автоматически не активируется.

Триггеры блокируют изменения/удаление данных ready/failed-наборов, изменение завершённого result_sets и удаление истории наборов; реестр classes неизменяем после вставки. SQL-проверка перехода ready дополнительно требует полное заявленное покрытие. Активный указатель принимает только ready.

`activate(db, result_set_id)` повторно валидирует набор и атомарно меняет singleton вместе с добавлением записи переключения в BEGIN IMMEDIATE. Повторная активация того же ID — no-op. Откат — activate прежнего ready ID, без перестроения или удаления. Внешние потребители должны фиксировать один ID на весь запрос; подключение веб/бота к новому каталогу относится к следующим этапам, на этапе 2 не выполнялось.

## Общая служба поиска — этап 3

Публичный Python API: `market_system.search.Catalog(db).search(SearchFilter(...), cursor=None, page_size=20, result_set_id=None) -> SearchPage`. Это одна служба для будущих веб- и Telegram-адаптеров. Она не зависит от aiogram/FastAPI и не выполняет сетевых запросов, обучения или извлечения признаков. Подключение интерфейсов и проверка ADMIN/USER относятся к этапам 4–5; старый бот пока использует прежний путь. На этапе 3 карточка возвращается внутри страницы поиска; этап 4 добавляет Catalog.get для отдельной страницы, повторно используя ту же загрузку карточки.

### Фильтр

- `post_type`: `vacancy`, `resume` или отсутствие ограничения. Идентификаторы `occupation_ids` — ANY; `skill_ids` — `skills_mode=ALL|ANY`, по умолчанию ALL. Пустой список не ограничивает выдачу. До 100 положительных целых ID каждого вида; дубликаты удаляются. Неизвестный ID или ID другого вида отклоняется. ID другого namespace не заменяется классом с похожим именем.
- `skill_roles`: по умолчанию required/preferred/possessed. Дополнительно всегда проверяется тип: у вакансии допустимы required/preferred, у резюме — possessed. Можно ограничить роли явно. Negated, task, mentioned и любые другие роли не участвуют в поиске. ALL считает различные class_id, поэтому две роли одного навыка не заменяют два навыка.
- `published_from` включительно, `published_until` исключительно. Сравнивается последняя известная дата публикации карточки. Вход — ISO datetime с явным timezone, нормализация в UTC. Для полного календарного дня нужно передать полночь начала и полночь следующего дня в нужном часовом поясе. Даты без timezone и пустой/обратный интервал отклоняются. Неизвестные даты не подменяются временем сбора.
- `work_format`, `schedule`, `employment_type`: точное совпадение с сохранённым значением. Значения не переводятся и не угадываются.
- `salary_min`: конечное неотрицательное число, обязательно вместе с `currency` и `salary_period`. Условие: `salary_from >= salary_min AND currency = currency_filter AND salary_period = period_filter`. Верхняя граница не заменяет нижнюю. NULL любого из этих трёх полей исключается всегда. Не выполняются курсовые, временные и gross/net-конвертации. Валюта и период без минимума отклоняются.
- `tax_mode=gross|net` — самостоятельное условие; отсутствие условия допускает оба режима и неизвестный. Оно может использоваться без зарплатного минимума.
- `unknown` — словарь политик для `post_type`, `published_at_utc`, `work_format`, `schedule`, `employment_type`, `tax_mode`. `exclude` (по умолчанию): неизвестное не удовлетворяет заданному условию. `include`: известное удовлетворяет условию либо поле NULL. `only`: только NULL, значение сравнения игнорируется. Без условия exclude/include не ограничивают поле; only работает и самостоятельно. Неизвестное означает SQL NULL. Для классов отсутствие связи — отсутствие подтверждённого совпадения, не wildcard; для зарплатного минимума политика всегда строгая. Попытки задать unknown-политику для классов, currency или salary_period отклоняются.

### Карточка, курсор и согласованность

- Одна строка страницы соответствует одному content_id. Возвращаются текст, компактные поля, все публикации этого текста в выбранном наборе (ID, URL, источник и нормализованная дата), классы с ID/namespace/ролью и evidence. `SearchPage` содержит `cards`, `next_cursor`, `result_set_id`, `revision`. Происхождение классификации и извлечения остаётся в evidence и result_sets.
- Порядок: `published_at_utc DESC, content_id DESC`; SQLite размещает NULL в конце DESC. Равные и неизвестные даты разрешаются уникальным стабильным content_id. Публикации внутри карточки сортируются по собственной дате DESC, publication_id DESC.
- Используется keyset-пагинация без OFFSET и COUNT всей выдачи. `page_size` — 1..100; запрашивается один дополнительный компактный ключ для определения продолжения. В конце `next_cursor=None`.
- Курсор содержит версию формата 1, SHA-256 канонического фильтра, ревизию и последний ключ сортировки. Ревизия включает ID готового неизменяемого набора, ready_at и версии; для активного режима — также номер последнего переключения. Переключение активного набора, включая уход и возврат, инвалидирует активный курсор. Явно заданный result_set_id фиксирует ready-набор и допускает продолжение после переключения активного указателя. Между активным и явно закреплённым режимом курсоры не переносимы. Размер страницы можно изменить.
- Повреждённый/несовместимый курсор вызывает `InvalidCursor` с сообщением «Курсор несовместим или повреждён. Начните поиск заново.». Курсор — непривилегированный маркер позиции, не средство авторизации и не подписанный токен доступа.
- Один вызов использует read-only SQLite и одну read-транзакцию: выбор набора, страницы и загрузка карточек видят согласованный снимок. До отбора `page_size+1` ключей тексты и evidence не загружаются. Готовые поисковые поля, состав публикаций и их даты неизменяемы по контракту этапа 2. Текущие URL/имена источников и текст читаются из базовых таблиц; самостоятельные изменения этих таблиц не создают исторический снимок их отображаемых значений.

### SQL и оптимизация

Классы ищутся исключительно по document_classes, с точными ID и ролями. Кандидаты без зарплатного минимума выбираются индексными подзапросами IN; ALL использует COUNT(DISTINCT class_id). При минимуме зарплаты явно выбирается диапазон catalog_salary через INDEXED BY, затем коррелированные EXISTS по связям; ALL требует отдельного EXISTS каждого навыка. Такой выбор устранённого узкого места обоснован измерениями этапа 3, но не является обещанием ускорения для любых распределений данных.

SQL-идентификаторы и операторы заданы кодом. Все пользовательские значения, class_id, лимит и ключ курсора передаются параметрами. Поиска через JSON, LIKE по названиям, перечитывания текстов или полнотекстового поиска нет.

Добавочная миграция 2: `python -m market_system.search.optimize [--db <локальная БД>]`, индекс `catalog_all_dates(result_set_id,published_at_utc DESC,content_id DESC)` для сортировки без ограничения типа. Сохраняется checksum SQL, транзакционность и проверка повторного запуска. Миграция 1 не изменена. Поиск сам не выполняет DDL. Данные/версии не меняются; код этапа 2 совместим с добавленным индексом.

Измерения и ограничения: `docs/STAGE3_BENCHMARK.md`, полные планы/SQL/параметры/сырые времена — `.artifacts/stage3-benchmark-v2/results.json`. Воспроизведение: `python scripts/benchmark_stage3.py --repeats 30 --output .artifacts/<новый-каталог>`. Скрипт создаёт Backup API копию только новой app.db и измеряет baseline/оптимизированный запрос с одинаковой семантикой; проверяет равенство полной упорядоченной выдачи. Существующий каталог результата не перезаписывается.

## Веб-интерфейс и доступ — этап 4

`market_system.web.app.create_app(WebConfig(...))` создаёт FastAPI/Jinja2-приложение. Импорт не запускает сервер и не открывает БД; состояние инициализируется в lifespan или явной CLI-командой. Веб читает каталог через `Catalog.search`, а карточку — через новый `Catalog.get(content_id, result_set_id)`. Метод get использует прежнюю загрузку карточки в одной read-only транзакции и принимает только готовый явно указанный набор. Правила SearchFilter, SQL отбора, сортировки и курсоров не дублируются и не меняются.

### Страницы и права

- `GET /login`, `POST /login` — вход; публичной регистрации нет.
- `GET /` — обзор владельца: количество документов, обработано/без классов/ещё не обработано, статусы проверки, типы, последняя известная публикация, активный набор и модель. USER перенаправляется в каталог. Группы статусов не суммируются между собой. Свежесть оценивается по числу целых прошедших суток; время сбора, если отсутствует в данных, обозначено неизвестным. Будущие даты требуют проверки.
- `GET /catalog` — доступен ADMIN и USER. Обычная GET-форма преобразует только типы параметров и передаёт SearchFilter общей службе. Профессии/навыки выбираются по ID; небольшой JS ищет только по уже загруженному списку классов, не по текстам публикаций. Даты формы означают границы суток UTC: «с» включительно, «до» исключительно. Все условия и размер страницы сохраняются в ссылке продолжения. Изменение фильтра обычной формой начинает новый поиск без курсора. Неверный/несовместимый курсор возвращает HTTP 400 и ссылку начала поиска заново с сохранёнными фильтрами.
- `GET /cards/{content_id}?result_set_id=...` — исходный текст, все публикации и безопасные ссылки, поля, классы и роли, сохранённые evidence и версии. Выбранный набор закреплён в ссылке; отсутствующая карточка или неготовый набор дают 404. Оценки модели не объявляются точностью; машинные результаты не объявляются подтверждённой разметкой.
- `GET /settings`, `POST /settings` — только ADMIN. Проверка на сервере действует для обоих методов; при записи повторно проверяется активная роль владельца в транзакции. USER получает 403 даже с собственным действительным CSRF-токеном. Меняются реально используемые параметры: размер страницы 1..100, тип публикации по умолчанию, порог свежести 1..3650 дней. Изменения немедленно применяются к новым запросам без явных параметров. Сохраняются предыдущие/новые значения, автор и время; revision защищает от перезаписи устаревшей формой.
- `POST /logout` — выход с CSRF и удалением сессии на сервере. GET не выполняет выход.

### Учётные записи, сессии и CSRF

Веб-состояние отделено от каталога: по умолчанию `state/web.db`, таблицы web_users, web_sessions, web_login_attempts, web_settings, web_settings_audit. Совпадение пути состояния с путём каталога запрещено. Создание таблиц идемпотентное, app.db вебом не мигрируется. Роль ADMIN/USER и active всегда читаются с сервера; cookie не содержит роль или данные пользователя.

Пароль обрабатывает `argon2-cffi.PasswordHasher` (Argon2id, библиотечная соль и параметры). CLI допускает 0..1024 символа, включая пустой пароль, логин — 3..64 латинские буквы/цифры/точка/дефис/подчёркивание. Повторный логин не перезаписывает существующий пароль. При успешном входе возможен библиотечный rehash. Неизвестная учётная запись проверяется с dummy-хешем; пользователю возвращается одинаковое сообщение об ошибке. После пяти неверных попыток вход по данному логину ограничивается до конца пятиминутного окна.

Токен сессии — 32 случайных байта, URL-safe; в БД хранится только SHA-256 токена. При входе прежняя анонимная сессия удаляется, токен меняется. Анонимная форма входа живёт 10 минут; авторизованная сессия — 8 часов без автоматического продления. На каждом запросе проверяются существование, срок и active пользователя. Смена роли/отключение учётной записи учитывается на следующем запросе. Выход отзывает токен на сервере. Cookie — HttpOnly, SameSite=Lax, Path=/; Secure включается для HTTPS через настройку окружения. На локальном HTTP Secure выключен, иначе браузер не сможет передать cookie.

Все изменяющие формы, включая вход, требуют случайный CSRF-токен из серверной сессии; сравнение constant-time. Явный чужой Origin запрещён. Отсутствующий Origin и `Origin: null` (встроенный браузер) допускаются только с действительной сессией и совпавшим CSRF-токеном: это не обход основной проверки. Токены не передаются через URL. POST принимает только application/x-www-form-urlencoded, ограничивает размер формы, число полей и повторы ключей.

Секретов и паролей по умолчанию в коде нет. Отдельный ключ подписи cookie не нужен: сессия хранится на сервере и подтверждается случайным непрозрачным токеном. Рабочие аккаунты не создаются автоматически. Файлы state и .artifacts исключены из Git.

Jinja2 autoescape экранирует исходные тексты, названия источников и evidence; HTML/Markdown публикаций не исполняется. Активные ссылки допускаются только для http/https, внешние ссылки получают noopener/noreferrer. CSP запрещает inline-скрипты и встраивание во фрейм; включены nosniff, no-referrer, no-store для страниц. Малый JavaScript служит только подсказкам классов; фильтры и формы работают без него.

```powershell
Set-Location 'C:\Study\MatchArt\labor_market_system'

```

Для учётной записи поиска: `python -m market_system.web create-user <логин>`. Автоматизированное предоставление пароля возможно через `--password-env <имя-переменной>`, но не через аргумент с самим паролем. `--state` у команд создания аккаунтов должен совпадать с состоянием сервера.

Пути ограничены новым проектом. `serve --host ... --port ...` позволяет явно изменить адрес; настройка внешнего HTTPS-развёртывания не выполнялась на этом этапе. Токены Telegram, фоновые задания, обработка, смена активного набора и другие будущие функции не представлены неработающими кнопками.


## Постоянные задания — этап 5

Текущий запрос изменил порядок этапов: очередь реализована сразу после веба, Telegram остаётся отложен.

`Jobs(db).initialize()` применяет миграцию 3 транзакционно и сверяет checksum. Новые таблицы jobs, job_inputs, job_publications, job_attempts, job_models находятся в app.db, чтобы результаты и checkpoint имели одну транзакционную границу. Веб теперь пишет только миграции/очередь/построение снимка запроса в app.db; поиск остаётся read-only. Учётные записи остаются в state/web.db. Веб не выполняет ML.

`Jobs.submit(kind, ids=None, batch_size=64, actor=..., idempotency_key=None)`:

- full: фиксирует весь текущий корпус, не принимает ids;
- incremental: требует совместимый активный набор той же модели. Без ids выбирает новые документы; с ids повторяет выбранные, включая все новые документы. Неизменённая часть копируется из активного ready-набора. Публикации повторно используемых документов сохраняются из базового набора; анализируемые документы получают снимок публикаций на момент submit;
- sample: 1..100 явных ID, готовый результат можно читать по result_set_id, но запрещено активировать;
- batch_size 1..512. Неизвестные ID и несовместимые версии отклоняются. Один idempotency_key допускает только тот же запрос того же автора. ModelVersion и manifest не создаются заново для очередной порции; job_id одновременно обозначает независимый прогон извлекателей;
- ID входов, хеш текста, публикации, версия модели/словарей/кода и последняя подтверждённая человеческая ревизия фиксируются до исполнения. Добавленные после submit документы не входят в задание. Отсутствующие классы представляются status=no_classes;
- историческая политика этапа 5: исправления читались из research/review/annotations.sqlite при submit. Начиная с этапа 7 применяется контракт единой проверки ниже: архив не является изменяемым источником исправлений; актуальные подтверждения накладываются также при завершении обработки и активации.

`Worker(Jobs(db)).run()` — отдельный CLI-процесс. Блокировка ОС на `<db>.worker.lock` держится всё время работы. После аварии ОС освобождает блокировку; следующий worker записывает interrupted в историю попытки и продолжает с checkpoint. Захват — BEGIN IMMEDIATE, уникальный running и новый owner UUID. Устаревший owner не может коммитить. Таймаут аренды не используется: зависший живой worker требуется завершить оператору, второй его не перехватывает.

Модель загружается лениво один раз для каждого fingerprint в процессе; повторные задания используют загруженный анализатор. Проверка артефактов выполняется перед первой загрузкой. Каждый пакет через скопированный LaborMarketPipeline.transform обрабатывается вне транзакции и вне HTTP. Результат каждого текста должен быть полным; размер результата равен размеру пакета. Запись всех проекций и checkpoint атомарна; при ошибке запись пакета откатывается, предшествующие пакеты сохраняются.

`cancel(id)` немедленно отменяет queued/failed; для running устанавливает cancel_requested. Исполнитель проверяет флаг перед анализом, перед записью и перед завершением. `retry(id)` допускает failed/cancelled и продолжает тот же снимок/набор с последнего checkpoint, увеличивая attempts при новом захвате. Failed/cancelled набор остаётся building, поэтому не виден в поиске. Succeeded нельзя повторно поставить в очередь: для нового анализа создаётся новое задание.

Ready проверяется по точному множеству job_inputs.content_id, количествам processing/catalog/evidence, статусам связей, FK, публикациям и полному прогрессу. SQLite-триггер дополняет проверки покрытия и запрещает активацию sample. Рабочий ready-набор неизменяем и остаётся активным, пока владелец явно не выберет другой через существующий activate. Автоматической активации нет.

ADMIN имеет GET /jobs, GET /jobs/{id}, POST /jobs, POST /jobs/{id}/retry и /cancel. Все POST требуют сессию ADMIN и CSRF; USER получает 403. Только конфигурация runtime.json определяет доверенную модель, веб-форма не принимает путь к pickle/joblib. Прогресс обновляется при обновлении страницы. Запуск веба не создаёт процесс исполнителя.


## Управляемые источники и сбор — этап 6

Миграция 4 добавляет managed_sources, collection_jobs, collection_attempts, publication_revisions, current_publications и collection_handoffs. Она не запускает сбор и не создаёт фиктивные публикации. Применяется через Sources.initialize, lifespan веба или запуск worker. Миграции 1–3 не переписываются.

Sources.save(kind, name, address, settings, enabled=True, schedule_enabled=False, interval_seconds=3600, source_id=None, revision=None) принимает только telegram/designhunters. Telegram — публичный HTTPS-адрес t.me/<channel>; DesignHunters — HTTPS designhunters.ru и локальный CSV с URL того же домена. Произвольные платформы/секреты/внешние пути запрещены. Настройки редактируются с optimistic revision. Идентичность существующего источника неизменна. Изменять параметры при queued/running нельзя; отключить источник можно, остановка произойдёт между пакетами.

Разрешённые параметры и значения по умолчанию:

- Общие: batch_size=50 (1..200), max_items=1000 (1..100000).
- Telegram: overlap_days=3 (1..30), overlap_limit=500 (1..5000).
- DesignHunters: обязательный csv_path, timeout_ms=30000 (1000..120000), delay_seconds=2 (0..60).

Sources.enqueue(source_id, mode='new', actor=...) фиксирует конфигурацию, курсор и список URL. history загружает историю порциями; new собирает новые наблюдения. Повтор enqueue при активном задании того же источника возвращает существующий job_id, независимо от mode. Состояния queued/running/succeeded/failed/cancelled, owner, attempts, progress/batches, времена и ошибки сохраняются в SQLite. Retry failed/cancelled продолжает тот же cursor/config только если версия курсора и настройки источника не изменились.

Telegram history сохраняет offset последнего просмотренного сообщения и high_water максимального ID. new сначала перечитывает ограниченное недавнее окно, затем идёт по ID выше high_water в возрастающем порядке до верхней границы запуска. Источник новых сообщений не считается инициализированным до первой порции history. Сообщения без текста пропускаются с продвижением курсора после коммита. Нет гарантии обнаружения правок вне окна, недоступных сообщений и удалений.

DesignHunters использует существующий _parse_page и фиксированный список URL из первого столбца CSV без заголовка. history продолжает индекс списка, new циклически перечитывает список с сохранением позиции между ограниченными порциями. Это локальный checkpoint, не upstream-курсор сайта. Новый список меняет hash и начинает новый проход. Автоматическое обнаружение URL не реализовано.

Publication сохраняет исходную строку. PublicationRevision — append-only связь publication_id/revision/content_id, дата публикации, observed_at, external_id, collection_job_id. Первая встреча legacy-публикации создаёт исходную ревизию с observed_at=NULL; это неизвестное время, а не время нового наблюдения. current_publications показывает последнюю связь. Точные повторы URL/текста/даты идемпотентны; возврат к старому тексту добавляет ревизию, но использует прежний Content. Исходные Content не переписываются. Legacy-нормализация hash не объединяет различные исходные тексты: whitespace-правка получает отдельный Content.

Пакет сохраняет публикации, ревизии, курсор источника/задания, прогресс и handoff одной BEGIN IMMEDIATE транзакцией. До commit cursor не продвинут; ошибка откатывает пакет целиком. Уже завершённые пакеты и другие источники не затрагиваются. Один worker этапа 5 под общей OS-блокировкой исполняет оба вида заданий; отдельный процесс сбора или scheduler не нужен. Аварийные running восстанавливаются при запуске worker.

Handoff хранит ID изменённых/новых содержимых и processing_job_id. История сохранения не зависит от доступности ML. Ожидающие handoffs объединяются в incremental job; его создание и привязка handoffs коммитятся атомарно. Если нет совместимого активного набора, handoff остаётся ожидающим с ошибкой и повтором через 60 секунд; ADMIN может повторить передачу явно. Никакого автоматического full или переключения active_result_set нет.

Уточнение этапа 5: новые processing jobs теперь фиксируют текущие публикации для всего снимка, включая скопированную часть. Старые result_publications неизменны; validate принимает историческую связь из publication_revisions. Исторический Content может остаться в новом наборе с publication_count=0. Это сохранённое содержимое, а не заявление о текущей публикации. Данные ready-наборов не редактируются при сборе.

Расписание выключено по умолчанию. Интервал 60..31536000 секунд, next_run_at — UTC. Worker проверяет due-запуски; уникальный активный job на source_id исключает наложение ручного/планового/повторного запуска. При простое просроченное расписание создаёт один запуск, не серию пропущенных запусков. Выключенный источник/расписание не создаёт новые задания. Для исполнения нужен работающий worker.

ADMIN: GET /sources; POST /sources; POST /sources/{id}/collect; POST /collection/{id}/retry; POST /collection/dispatch. Все изменения требуют текущую ADMIN-сессию и CSRF. USER получает 403. Web не запускает Telethon, браузер или модель.

Локальные secret/session-файлы исключены из Git правилами state/ и *.session*. Для серверных прав доступа и эксплуатации требуется отдельный этап.
